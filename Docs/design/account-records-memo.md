# 库存数据管理备忘

## 库存批次与当前状态（2026-11-19）

- 本轮仅整理库存。CSV 标准名称继续作为物品关联键；状态灯只反映库存的错误、待核实、提醒和完成状态，不参与需求满足判断。核实、时间、到期、优先级及提示版本校验继续遵循下文规则。
- 新增 `InventoryRecordReference`（`BatchId + RecordId`）。一次总量上报、增量上报、采集失败、导入或人工修订具有批次身份；每个输入具有批次内标识。调用者可提供批次 ID，记录可提供 RecordId；未提供时分别生成批次 ID 和按输入顺序的编号。重传须复用身份，改变输入须使用新身份。
- 同组合 ID、同内容且已接受的输入不重复应用，也不复活已清理历史；同 ID 不同内容在业务变更前拒绝。相同失败输入允许依照原规则重新校验。既有来源、业务时间、内容指纹去重继续生效，不因换新 ID 重复累计。
- 活动事件继续具有独立 `Id` 和 `ContentVersion`。多个活动事件可引用同一条输入；`RecordReference` 指向来源输入，`VerificationReference` 指向核实或人工替代依据。`AttemptId`、`ErrorId`、`VerificationId` 暂保留用于旧数据及现有规则兼容，不直接全局改名。
- `inventory.json` 保存确认库存、当前处理状态、去重凭证，以及短暂的待发布批次／归档内容。批次原始输入及逐条结果存于 `batches/<BatchId 的 SHA256>.json`；使用摘要文件名避免 Windows 路径和大小写冲突，真实 BatchId 在文件内。原有 `events/<日期>.json` 继续保存可变事件的归档状态，不作为原始输入的唯一证据。
- 保存先原子提交当前状态、凭证和待发布内容，再幂等发布归档及批次，最后清除待发布标记；加载维护或写入时补齐中断操作。清除标记不覆盖上一版业务状态备份。纯展示 `ReadAsync` 不执行修复写入。
- `batch-index.json` 是可重建的物品历史索引。`GetItemHistoryAsync` 按物品分页查询，`GetBatchAsync` 查看同批记录。事件窗口可搜索组合 ID 并按需查看所属批次，普通库存页不读取批次历史。
- 历史沿用 `EventLimit`（默认 5000，范围 1000～50000）。批次历史按记录条数裁剪，可保留部分批次并记录原始／已清理条数。当前库存、保留事件、备份及日期快照引用的证据受保护；全部受保护时允许超过软上限。组合身份凭证暂保守保留，不随历史删除；用户明确删除物品时，仅重置该物品的接收状态以沿用旧规则，身份内容摘要仍保留。后续若压缩凭证，须先证明不会导致旧输入再次应用。
- 人工修订同样生成独立批次，保存原数量和实际确认时间；待核实事项仍按原规则终止，不冒充核实成功。界面相同内容的失败重试复用批次 ID，修改内容后生成新批次。
- 导入保留原来的分来源提交方式，不承诺整批回滚，但各来源和增量使用同一批次 ID。交换格式仍为 version=1，可选根字段 `batchId`、条目字段 `recordId`；普通导出仍只输出确认库存，不是完整备份。
- 当前库存存储升级为 schemaVersion=2，读取兼容版本 1；首次持久化补齐旧引用，保留旧事件 ID、业务时间和原始证据。无法确定真实批次的旧记录使用稳定的 `legacy-` 迁移批次，不按相近时间猜测关联。旧程序不应继续写入升级后的文件。
- 日期快照包含当前数量、错误、活动事件、提醒状态和对应引用，用于查看当时库存状态；完整恢复须备份整个账号目录及共享字典／配置，不能只覆盖一个旧库存快照。UID 改名、账号删除随目录覆盖新增历史；清空库存同时清理批次和索引。


- 验证：完整解决方案编译通过；库存、批次、状态策略、账号数据管理和独立 STA 界面测试共 161 项通过。未启动主程序，未迁移实际用户数据。

- 狛荷屋不再维护自己的 UID 列表。UID 下拉框列出 Pulonia 账户目录中填写了 UID 的账户，显示为“名称（UID）”，顺序与账户列表一致；打开页面时默认选中本实例当前账户。没有 UID 的账户不出现。
- 删除“新增 UID”浮窗，改为“管理账户”，跳转到 Pulonia 账户页。新增 UID 就是在账户页新增账户。
- 删除 UID 改在账户页删除账户，会一并删除该账户的狛荷屋记录。狛荷屋的账户菜单只保留“清空库存记录”。
- 在账户页修改 UID 时，该账户的狛荷屋数据目录随之改名；新 UID 已有狛荷屋数据时拒绝修改（统筹设计 4.1）。
- 导入交换文件时，文件中的 UID 不在账户目录里，就提示“创建账户“账户 尾号 5678”并导入？”，确认后先建账户再导入。

- 狛荷屋通过 `IPuloniaAccountService` 读取账户列表、订阅账户变化。狛荷屋依赖 Pulonia 账户服务，反过来不依赖。UID 修改和删除账户时，Pulonia 通过扩展点 `IPuloniaAccountDataHandler` 让狛荷屋改名或删除数据目录，狛荷屋的实现是 `AccountRecordsAccountDataHandler`。
- UID 列表只来自账户目录。磁盘上 `User/AccountRecords/<uid>/` 有数据、但账户目录里没有该 UID 时，狛荷屋不显示这份数据，也不自动建账户；要继续查看，在账户页新建填写该 UID 的账户。

## 已确认的处理规则（2026-10-29）

- 没有确认库存时仍保留有符号 delta，表格仅显示增减量，不建立零库存。JSON 导出仍仅包含确认库存。
- 失败 delta 可以重新校验；相同失败合并次数，修正或外部条件变化后成功接收则归档对应错误。已接收事件的同内容重传去重，内容变化报冲突，不覆盖、不重复累加。
- 上报使用实际发生或采集时间，保留足够精度，不以批量发送时间替换。总库存必须严格晚于它覆盖的 delta；相同时间提示先后不明。
- 到期信息是内置、默认隐藏的可选字段，不通过补充字典控制。已有到期信息时在现有编辑弹窗内展开数量与到期时间批次编辑；允许部分库存未注明到期时间，批次数量合计不得大于总数。
- 去重凭证暂不拆独立文件。历史 ID 在归档清理成功后删除；确认库存严格覆盖的 delta 凭证可清理，旧 delta 重放可能改为过早拒绝。未覆盖的有效 delta 仍保留去重。失败完整库存上报指纹暂保留。
- 旧版 delta 凭证为不可逆哈希；有对应事件时可迁移，已失去事件的凭证保守保留，不能猜测时间后删除。

## 历史错误核实后的提示

- 正常接收新的有效总库存后，该物品未归档 Error 转为历史证据，移除当前错误对象，并合并为 `VerifiedErrorWarning` 橘灯。
- 提示当前数量已核实，但不表示原错误正确。Warning 可确认归档；后续新错误仍亮红灯。重复旧库存不触发核实。

## 多事件展示

- 卡片捕获事件内容摘要；归档和舍弃在存储锁内整体校验展示版本，任何内容变化均拒绝整次操作。舍弃仅作用于卡片捕获的错误，后来新增的错误保留。

## 暂缓事项

- 补充字典可考虑增加仅供记录的扩展参数，不自动生成到期式分组管理，也不在本轮实现通用动态表头。
- 需求验证以后可利用增量（例如 +5）判断达标；涉及负数时报错的细则留待需求模块，本轮不实现。
- 本轮不改变 JSON 交换文件只导出确认库存的用途，不把导出视为完整状态备份。

### 物品详情展示保留历史（2026-11-19）

- 物品详情顶部单独展示当前确认库存，下方按处理时间倒序展示该物品的批次记录，涵盖总量、增量、采集失败和人工修订。
- 历史每页 50 条，可继续加载到全部保留记录；同页同批次只读取一次，失败可重试。原始输入和 BatchId / RecordId 默认折叠。
- 批次处理结果“已接收”不代表增量已核实；当前灯状态仍由原有事件规则决定。
- 旧版本已覆盖、历史保留策略已清理的数据不能恢复；查看窗口不主动执行旧数据迁移。

### 名称索引与图标复用（2026-11-19）

- CSV 按标准名称构建基础物品目录，补充字典叠加到该目录；不以 CSV 行号、训练枚举顺序或文件修改时间作为物品身份。
- 图标统一保存至 AccountRecords/icons/<名称 SHA-256>.png，不再以 CSV 修改时间建立版本子目录。首次访问一次性复制旧时间戳目录中的图标，同名优先较新目录，已有稳定目录文件不覆盖；旧目录保留至用户清理全部图标。迁移完成标记防止单项删除后旧图复活。
- 有效总量上报沿用现有分类补缺规则；同名已有非空分类冲突时不自动覆盖，产生分类提醒，数量单独校验。人工补充字典仍优先于 CSV；CSV 更新冲突由现有字典冲突检查提示，不静默覆盖人工修订。
- 这里的自动补缺目前指分类及伴随的来源备注，不表示所有 CSV 列都支持上报或自动合并；增量接口也不携带分类。

### 库存筛选器按实际记录显示（2026-11-19）

- 筛选器仅列出当前账号完整库存行中存在的背包页和材料类型，不再根据完整字典、空自定义页或固定未分类项生成空筛选项。
- 零库存、无确认总量的待核实增量、异常记录仍保留对应类型；搜索与勾选过滤不改变筛选项集合。
- 新增、删除及刷新库存时同步分类；现有分类保留勾选与展开状态，选中的分类全部消失时恢复全选。切换账号清空旧账号的分类，空账号不显示分类。

### 审查问题修复（2026-11-19）

- 物品历史首次加载时固定完整引用索引，随后每页 50 条；后台新增或失败记录重试不会使翻页漏项。新提交需重新打开查看；查看期间证据被清理时明确提示缺失条数。
- 旧来源记录没有 RecordReference 时仍显示在详情上方，不为了查看触发写入迁移。
- 库存导入分别合并分类和背包页：已有分类不阻止补齐空背包页；非空值冲突返回提醒并保留本地。补充字典显式 Page="" 表示人工设置未分类，自动输入不可覆盖。相同值重复导入不改写补充字典。
- 图标 Exists 只做 File.Exists，不写磁盘、不获取后台加载锁；旧目录接续仍由后台图标读取或写入入口执行，读取遇到权限错误回退占位。
- 自定义分类图标不再放入静态永久缓存，图片随绑定引用释放；静态共享仅用于有限的内置分页图标。

### 查询接口精简（2026-11-20）

- 移除 GetItemHistoryAsync 偏移分页入口。详情通过 GetItemHistorySnapshotAsync 固定索引，再通过 GetItemHistoryPageAsync 按引用读取整页；一页仅加载一次库存，同批证据只读一次，返回顺序与引用一致，已清理记录以 null 占位。
- GetBatchAsync 保留给事件窗口查看完整批次；物品详情不再逐批查询和自行拼装索引。
- 移除 GetCategoryCodesAsync，分类编辑器从 GetItemClassificationsAsync 的同一快照派生代码列表，保留未分类和自定义分类。
- 写入接口、交换协议、存储格式及历史排序规则保持不变。


### 开发期库存收紧（2026-11-20，取代上文冲突约定）

- 当前库存文档升级为 SchemaVersion 3。开发期不兼容旧记录：移除旧来源摘要、颜色状态、错误文本关联、历史时间解析、批次引用补齐及旧图标目录迁移；旧版本明确拒绝读取，不自动改写用户数据。
- 当前库存、批次输入证据、事件状态仍独立。错误只保存修订预填数量、冲突时库存快照及 RecordReference；原始输入从批次读取，不再复制进事件历史和错误对象。
- 物品详情只单列当前库存，其他来源观测统一在批次历史查看。内部最多五个近期来源观测暂留用于重复扫描去重，不再提供来源记录保留设置。
- 保留增量、核实、状态灯、人工修订和完整排查入口；不因增量使用较少而删减底层能力。
- 删除类别外观编辑器、自定义类别名称/备注/图标及对应存储；保留 CSV 与补充字典、物品分类修订、默认分类图标、按实际库存生成筛选器和物品图标缓存。
- 删除通用提醒规则引擎与规则文件编辑入口；库存错误、字典分类冲突、增量核实和内置到期检查继续生效。
- 开发期批次与事件全部保留，不按批次数或记录数自动裁剪；BatchReceipts 独立保留输入身份和去重凭证。删除旧裁剪专用凭证及配置。以后依据实际记录数、磁盘体积和查询耗时决定保留策略，不能直接删历史后允许旧增量重新入账。
- 日期快照继续单独管理，默认保留七个有记录日期、范围一至三十；减少日期快照不影响批次或事件历史。保留原子写入、业务备份、待发布归档/批次及中断恢复。

### JS 库存入口（2026-11-21）

- 仅提供 `inventory.report(records)` 与 `inventory.getQuantities(nameOrNames)` 两个业务入口；参数和返回值均为原生 JS 数组/对象，无需调用方序列化 JSON。
- 写入数组每项使用 `name`、`quantity`、`recordedAt`。省略 `type` 或填写 `snapshot` 表示实测总量；`type: "delta"` 表示有符号增量。未知字段、未知类型、非整数数量或超出 JS 安全整数范围会拒绝整次调用，避免默默误解输入。
- 复用现有 `category`、`comment`、`expirations: [{ quantity, expiresAt }]`，不引入 details。增量不接收 category/comment。实际采集/变动时间 recordedAt 必须带时区；业务不合法的记录仍交给原库存逻辑留存异常并返回逐条结果。
- 到期分组沿用现有校验：数量为正、日期带时区、合计不超过上报数量，最多 100 组。未覆盖部分的到期时间未知。
- 宿主绑定游戏 UID、来源、批次和记录身份。Pulonia 使用节点前已核验的 UID，不把 AccountId 当 UID；无已核验 UID 的入口在首次库存访问时识别当前 UID，识别失败拒绝操作。绑定后同一次脚本不得自行切换游戏账号。
- Pulonia 的 `RunId + TaskAddress + Attempt` 生成稳定 BatchId；分组轮次已包含在 TaskAddress。直接执行脚本每次生成独立 BatchId。同次执行多次提交共用批次，RecordId 连续递增；脚本不传入这些标识。重复调用表示新的记录，不是请求重传凭证。
- 同数组按输入顺序处理，不按类型分组、不按物品去重；并发调用由宿主串行执行。业务拒绝不阻止后续记录。数组不是全有或全无事务，取消或存储异常时已提交记录保留，不应盲目重试增量。
- 写入返回 batchId、records（逐条 recordId/name/outcome/message 等）、accepted、rejected、warnings 及重复统计。数量处理成功不等于增量已核实；同物品多条记录的结果以 records 为准。
- 查询单个名称和名称数组都返回名称到数量的映射；只读本地最后确认数量，不叠加待核实增量，不扫描游戏库存；无记录为 null，确认零库存为 0。

```js
const recordedAt = new Date().toISOString(); // 在实际采集或变动发生时记录
const result = await inventory.report([
    { name: "摩拉", quantity: 100000, recordedAt },
    { name: "甜甜花", type: "delta", quantity: 5, recordedAt }
]);
const counts = await inventory.getQuantities(["摩拉", "甜甜花"]);
```

### JS 扫描阶段分批（2026-11-21）

- `inventory.report(records, { batch: "before" })` 可选指定本次执行内的分组名；省略 options 或使用 `{}` 仍归入默认批次。分组名为 1～128 个字符的非空字符串，精确匹配、区分大小写，支持中文；不支持的选项或无效分组名在写入前拒绝。
- 实际 BatchId 由执行身份与分组名共同生成。同次执行同名分组追加到同一批次，不同分组独立；不同节点、轮次、重试或直接运行仍隔离。分组名不是可指定的外部 BatchId。
- 分组同时适用于实测和增量；RecordId 仍在本次执行中连续递增，切换分组不重置。分组只划分追溯批次，不隔离当前库存或改变增量核实逻辑。

```js
await inventory.report(beforeItems, { batch: "before" });
// 执行任务后，重新扫描并记录本次采集时间。
await inventory.report(afterItems, { batch: "after" });
```
